## Dual-Write Strategy (Documented)

**Architecture:**
```
publishEvent(event) {
  1. Redis publish (fast path — real-time delivery to subscribers)
  2. Supabase insert (durable path — audit log, replay capability)
}
```

**Error handling:**
- Redis publish fails → event is lost (acceptable for current scale)
- Supabase write fails → logged, event flow continues (durable path is supplementary)

**Supabase schema pending from Ahmad:**
- `events` table needs columns: `event_id`, `event_type`, `source`, `payload`, `correlation_id`, `caused_by_job_id`, `hop_count` (PENDING), `processed_at` (PENDING), `processed_by` (PENDING), `created_at`
- Code currently writes to confirmed columns only; update insert when schema is ready

---

## Decisions Made

1. **Dual-write is non-blocking on Supabase failures** — event flow continues even if Supabase write fails. Rationale: Supabase is for durability/audit, not operational correctness.

2. **WEBHOOK_INTERNAL_SECRET validation at startup** — phase3-integration.ts refuses to start if the default dev value is detected. This prevents accidental deployment with insecure defaults.

3. **Catch-all handler logs all non-job events** — for development visibility. Should be disabled in production to reduce log noise.

4. **Queue alert cooldown of 5 minutes** — prevents alert spam if queue depth stays elevated.
