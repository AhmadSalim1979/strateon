### moosa-worker.json (Separate File)

There's a **second file** at `/home/node/.openclaw/workspace/state/heartbeats/moosa-worker.json` with a different format (`{component, last_run_at, status, pid}`). This is what the stale-task-detector reads via `PM2_HEARTBEAT_PATH`.

This file was last updated **May 17 08:22** (not May 15) — it contains "Worker online. Heartbeat refreshed" from some prior recovery attempt. This is a **separate heartbeat mechanism** from the watchdog's `worker.json`.

**Two heartbeat files, two purposes:**
- `worker.json` — watchdog's primary stale detection (May 15 18:23, stale)
- `moosa-worker.json` — stale-task-detector's worker health check (May 17 08:22, stale)

### Why Stale May 15 Heartbeat Persisted

The worker's `writeCycleHeartbeats()` is correctly called before every `run_self_check_and_decide` return. But:

1. **May 15 18:23 crash** — worker crashed during TD-Codex init, BEFORE any `run_self_check_and_decide` execution. Heartbeat was written as `UNHEALTHY` during crash.
2. **May 17 19:48 current restart** — worker started but has not successfully executed `run_self_check_and_decide` because:
   - No `self-check-trigger.json` fires without an external cron
   - Task queue may be empty (no pending tasks claimed)
   - Worker polls every 10s but gets "No pending tasks, cycle complete" — which does NOT write a heartbeat
3. **Heartbeat only written on `run_self_check_and_decide` completion** — not on every poll cycle

**Root cause:** The worker only writes a heartbeat when `run_self_check_and_decide` executes (after a self-check trigger fires or a thinking_loop task runs). Plain poll cycles do NOT update the heartbeat.

### Alert Cooldown Logic

```javascript
const ALERT_COOLDOWN_CYCLES = 4;  // ~12 minutes at 3-min interval

function canFireAlert(state, alertKind) {
  return state.alert_counts[alertKind] === 0 ||
         state.consecutive_failures[alertKind] >= cooldown;
}
```

**Alert fires when:** `alert_counts[alertKind] === 0` (first ever alert) OR `consecutive_failures >= 4`.

const WATCHDOG_ALERTS_ENABLED = process.env.WATCHDOG_ALERTS_ENABLED === 'true';

async function fireAlert(message) {

**Watchdog IS functioning correctly.** It detects stale, increments counters, logs findings. It just doesn't send alerts because `WATCHDOG_ALERTS_ENABLED=false`.

## 4. Controlled Alert Enablement Design

### Current State

- Watchdog has detected 563 consecutive stale failures
- Alert counts are at 281 each
- Alerts are disabled

**If we enable alerts now:** The first alert fires immediately (alert_counts[kind] === 0 condition). Then every ~12 minutes thereafter. This creates an immediate storm of alerts about the May 15 stale heartbeat.

### Recommended Staged Enablement Procedure

**Phase A — Reset Watchdog State (No Alerts Yet)**

Before enabling, reset the watchdog-state.json to clear the 563 consecutive failure count:

1. Read current watchdog-state.json
2. Reset `consecutive_failures` to `{ worker_heartbeat_stale: 0, selfcheck_stale: 0 }`
3. Reset `alert_counts` to `{ worker_heartbeat_stale: 0, selfcheck_stale: 0 }`
4. Write clean state file

**Why:** The consecutive failure count is a historical artifact from 3 days of staleness. We don't want to count pre-enablement failures toward the cooldown. Fresh start.

**Phase B — Verify Worker Can Write Fresh Heartbeat**

Before enabling alerts, verify the worker's heartbeat mechanism works:

1. Manually trigger a self-check cycle (or confirm task queue has pending work)
2. Verify `worker.json` gets a fresh `_written_at` timestamp within 60 seconds
3. Confirm watchdog detects the fresh heartbeat (not stale)

**If heartbeat doesn't refresh:** Do not enable alerts. Investigate why `run_self_check_and_decide` isn't executing.

**Phase C — Enable Alerts With Cooldown Protection**

Enable via PM2 env variable:
```
WATCHDOG_ALERTS_ENABLED=true
```

The cooldown mechanism (4 cycles = ~12 min) prevents alert storms. With fresh heartbeat confirmed, the next stale detection would only occur if worker actually goes down.

**Phase D — Verify Alert Fires Cleanly**

1. Confirm alert received on WhatsApp
2. Confirm watchdog-state.json alert_count incremented
3. Confirm no duplicate alerts within 12-minute window

**Phase E — Rollback Procedure**

If alerts are noisy or false positives detected:

```javascript
// Immediate rollback:
WATCHDOG_ALERTS_ENABLED=false  // in PM2 env
// Or: pm2 restart moosa-watchdog with env.WATCHDOG_ALERTS_ENABLED not set
```

### Alert Message Design

Current alert would say:
```
⚠️ MOOSA Worker heartbeat STALE (563x stale detection). (was PID 922274) last cycle at 2026-05-15T18:23:27.644Z
Reason: heartbeat age 3460min > 10min. Worker may be dead or stalled. Manual check required.
```

**Problem:** This references the stale May 15 heartbeat and the OLD PID (922274 vs current 1012415). The message is misleading because:
1. Worker IS currently online (PID 1012415)
2. Heartbeat is stale from May 15, not from current runtime

**Recommendation:** Fix the alert message to reference current PID, or suppress this specific alert (worker IS alive, just not writing heartbeats). The worker being "stale" doesn't mean it's dead — it means it hasn't run self-check.
