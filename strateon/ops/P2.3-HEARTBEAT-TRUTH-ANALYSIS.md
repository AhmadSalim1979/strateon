# P2.3 — HEARTBEAT TRUTH ANALYSIS
**Topic:** Worker liveness heartbeat semantic clarification | **Date:** 2026-05-18

---

## Executive Answer

**This is a partial R4 implementation gap — NOT a regression, NOT intentional architecture.**

The watchdog's `worker.json` heartbeat is **only written during `run_self_check_and_decide` execution**. Normal poll cycles do not write it. This means during idle healthy operation (no pending tasks, no self-check trigger), `worker.json` stops updating immediately and becomes permanently stale within 10 minutes — even though the worker is fully alive and working correctly.

**The critical finding:** The architecture as implemented cannot distinguish between:
- A healthy worker that is simply idle
- A hung worker that has stopped processing
- A blocked scheduler
- A dead worker

All four produce **identical stale `worker.json` signals**.

## Q1: What component represents what

### worker.json (what watchdog reads)

| Intended to represent | ACTUAL behavior |
|---|---|
| Worker liveness | ❌ Only updated during `run_self_check_and_decide`, not during normal poll cycles |
| Cycle liveness | ❌ No heartbeat written on poll cycle completion |
| Self-check liveness | ✅ Self-check path: writeCycleHeartbeats() is called on every `run_self_check_and_decide` return |
| Task execution liveness | ❌ Not written during `processTask()` |

**Verdict:** `worker.json` is semantically broken as a worker liveness signal. It only advances when self-check runs, not when the worker does normal work.

### self-check.json (what watchdog reads)

| Intended to represent | ACTUAL behavior |
|---|---|
| Self-check subsystem alive | ✅ Updated by `writeSelfCheckHeartbeat()` called on every `run_self_check_and_decide` completion |
| Self-check scheduler | ⚠️ Depends on `run_self_check_and_decide` execution AND self-check-trigger.json |

**Verdict:** `self-check.json` is a reliable self-check indicator IF self-check triggers are firing. But during idle periods, it also goes stale.

### moosa-worker.json (what stale-task-detector reads)

| Intended to represent | ACTUAL behavior |
|---|---|
| Worker status | ⚠️ Unknown writer — format `{component, last_run_at, status, pid}` differs from heartbeat-writer output |
| Last refreshed | Last updated May 17 08:22 — shows `status: "online"` and `note: "Worker online. Heartbeat refreshed"` |
| Source | Cannot be traced to any current source file |

**Verdict:** `moosa-worker.json` appears to be written by a different, older mechanism. Current stale-task-detector reads `content.timestamp` but the file uses `last_run_at` — the detector reads the wrong field.

## Q2: Should worker.json advance every poll cycle or only during self-check?

**Answer: Every poll cycle — the current behavior is wrong.**

The comment in `run_self_check_and_decide.js` says:
> "Write worker and self-check heartbeats before returning from any exit path. Called before every `return result;` to ensure watchdog always sees fresh heartbeats regardless of which code path exits the handler."

This comment indicates the **intended design** was for `writeCycleHeartbeats()` to fire on every `run_self_check_and_decide` completion — but `run_self_check_and_decide` is **not called during normal poll cycles**. It's only called when a self-check trigger fires.

The `runCycle()` function shows:
```javascript
if (pendingTasks.length === 0) {
  log('No pending tasks, cycle complete');
  return { processed: 0, succeeded: 0, failed: 0 };  // ← No heartbeat written
}
```

**The fix should be:** Add a lightweight heartbeat write to `runCycle()` on every poll cycle completion — not dependent on task execution.

## Q3: If worker.json intentionally does NOT advance during idle healthy operation — how can watchdog distinguish healthy idle from hung/dead?

**Answer: It CANNOT. The current architecture cannot make this distinction.**

This is a fundamental design flaw. The watchdog's stale detection is:
```javascript
const ageMs = Date.now() - new Date(hb.last_cycle_at || 0).getTime();
return { stale: ageMs > STALE_WORKER, ... };  // STALE_WORKER = 10 minutes
```

A 10-minute threshold means: if the worker has not run `run_self_check_and_decide` in the last 10 minutes, it reports stale — **regardless of whether the worker is polling and processing tasks normally**.

**Current worker behavior:**
- Poll interval: 10 seconds
- Normal idle: "No pending tasks, cycle complete" every 10 seconds
- `run_self_check_and_decide` only fires when `self-check-trigger.json` exists
- Self-check trigger written by OpenClaw cron (which may not be running frequently)
- **Result:** `worker.json` can go stale in under 10 minutes during normal idle operation

**The watchdog alert "Worker may be dead or stalled" is completely unreliable** during normal operation.

## Q4: Does current architecture permit false stale states while runtime is healthy?

**YES — definitively.**

Current evidence:
- `worker.json` last written: May 15 18:23 UTC
- Current worker PID 1012415: online, polling, healthy, 10h uptime
- Watchdog-state.json: 563 consecutive stale detections, worker is NOT dead or stalled
- moosa-worker.json shows `status: "online"` with recent `last_run_at`

**The architecture produces FALSE stale alerts continuously.** This is why `WATCHDOG_ALERTS_ENABLED=false` — if enabled, the worker would receive alert spam every ~12 minutes indefinitely.

## Q5: Would enabling alerts now generate false positives?

**YES — guaranteed.**

If alerts are enabled now with the current stale `worker.json` (May 15, 72+ hours old):

1. First alert fires immediately (alert_counts[kind] === 0 condition met)
2. Alert message: `⚠️ MOOSA Worker heartbeat STALE (563x stale detection). (was PID 922274) last cycle at 2026-05-15T18:23:27.644Z. Reason: heartbeat age 3460min > 10min. Worker may be dead or stalled. Manual check required.`

**This is a false positive.** The worker is alive (PID 1012415, 10h uptime, polling successfully). The May 15 PID 922274 is the OLD crashed worker. The heartbeat is stale because self-check hasn't run, not because the worker is dead.

**Subsequent alerts:** Every 4 watchdog cycles (~12 minutes), the stale alert would fire again indefinitely until:
- A `run_self_check_and_decide` executes and writes fresh `worker.json`, OR
- The stale detection is fixed architecturally

## Q6: Minimum correct architectural fix before watchdog alerts become trustworthy

### Option A (Minimal — adds heartbeat to poll cycle)

**In `loop.js` `runCycle()` — write heartbeat on every cycle completion:**

```javascript
// At end of runCycle(), after "No pending tasks, cycle complete"
if (pendingTasks.length === 0) {
  log('No pending tasks, cycle complete');
  // ADD: Write worker heartbeat so watchdog knows worker is alive
  await writeHeartbeatToFile({
    process_name: 'worker',
    pid: process.pid,
    last_cycle_at: new Date().toISOString(),
    last_status: 'IDLE',
    cycle_count: iterations,  // from startWorker scope
  });
  return { processed: 0, succeeded: 0, failed: 0 };
}
```

This requires importing `writeHeartbeatToFile` into `loop.js`.

**Pros:** Minimal change, restores heartbeat on every poll cycle
**Cons:** Does not solve self-check path gap (self-check.json still only updates on `run_self_check_and_decide`)

### Option B (Preferred — separate worker liveness from self-check execution)

**Two distinct heartbeats:**

1. **Worker heartbeat (worker.json):** Written every poll cycle by `loop.js`. Represents "worker process is alive and polling." Never goes stale during normal operation.

2. **Self-check heartbeat (self-check.json):** Written only on `run_self_check_and_decide` execution. Represents "self-check logic ran and produced a decision." Can go stale legitimately between self-check runs.

**Watchdog interpretation:**
- `worker.json` stale → worker is definitely dead (immediate critical alert)
- `worker.json` fresh, `self-check.json` stale → self-check subsystem not running (informational alert, not critical — worker is alive but self-check hasn't fired)

### Option C (Watchdog threshold fix — lowest risk)

**Change `STALE_WORKER` from 10 minutes to 120 minutes:**

This acknowledges that `worker.json` only advances on `run_self_check_and_decide` which may not fire frequently. With a 2-hour threshold, the watchdog only alerts when the worker has been truly unresponsive for an extended period.

**Pros:** Zero code changes, eliminates false positives from idle operation
**Cons:** Delays detection of actual worker death from 10 min to 120 min

## Recommended Minimum Fix (Before Alert Enablement)

**Implement Option B — Separate worker liveness from self-check execution:**

1. **`loop.js`**: Add heartbeat write on every poll cycle (every 10 seconds) — worker is alive
2. **`run_self_check_and_decide.js`**: Continue writing `self-check.json` on self-check completion
3. **`watchdog.js`**: Update alert semantics — `worker.json` stale = worker definitely dead (critical), `self-check.json` stale = self-check not running (informational)
4. **`moosa-worker.json`**: Deprecate and remove from stale-task-detector (duplicate/misleading signal)

**Why Option B is correct:**
- Worker liveness should not depend on task execution
- Self-check execution should not block worker liveness signal
- Clear separation of concerns: liveness vs. scheduled-task execution
- Watchdog can now make accurate binary判断: worker alive vs. worker dead
