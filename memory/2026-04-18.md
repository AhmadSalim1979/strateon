## R3: Prioritization Weight Calibration — COMPLETED (18 April 2026, 20:45 UTC)

### Design
- **Calibration method:** Scenario-based benchmark harness — each scenario defines items with known properties and expected ordering. Actual ordering computed from weights is compared against expected. Mismatch = calibration failure.
- **Weight storage:** `config/priority-weights.json` — versioned, operator-reviewed, with explicit rationale per factor group.
- **Versioning:** Each config has `version`, `author`, `created_at`, `description` fields. No auto-increment — operator assigns version on edit.

### Weight Model
- Factor dimensions: status (35%), recurrence (25%), trend (20%), blocking (10%), residual (10%)
- Status: CRITICAL=1.0, UNHEALTHY=0.85, DEGRADED=0.6, HEALTHY=0.1
- Recurrence: chronic=1.0, persistent=0.75, recurring=0.5, first_seen=0.1
- Trend: worsening=1.0, stable=0.5, improving=0.2
- Blocking: yes=1.0, no=0.3
- Reactive bonus: +0.2; Friction: low=+0.1, moderate=0, high=-0.15
- Judgment bonus: capped at 0.15, scaled by score × 0.05

### Files Changed
- `config/priority-weights.json` — NEW (operator-reviewed weight config v1.0.0)
- `scripts/priority-calibration.js` — NEW (calibration harness with 6 benchmark scenarios)
- `src/handlers/priority-manager.js` — Modified (loads from config instead of hardcoded WEIGHTS; exports `getWeightConfig()`; adds `_weight_version` to output)

### Benchmark Set (6 scenarios)
1. Critical reactive outranks healthy initiative ✅
2. Unhealthy persistent outranks degraded recurring ✅
3. Two initiatives ranked by confidence + friction ✅
4. Worsening trend beats stable despite lower recurrence ✅
5. Chronic blocking outranks persistent non-blocking ✅
6. Degraded worsening outranks degraded improving ✅

### Safety Confirmations
- No autonomous weight mutation ✅ (config is read-only at runtime, edited by operator)
- No approval changes ✅ (approval gating unchanged)
- No hidden self-tuning ✅ (weights fixed per config version)
- Calibration harness is read-only — produces reports, doesn't mutate weights ✅

### Residual Limitations
- Weights are still invented (v1.0.0 baseline) — calibration ensures consistency, not ground truth
- Calibration scenarios hand-authored by Moosa; operator should review and adjust
- Score formula is fixed; nonlinear interactions between factors not modeled
- Real-world production data would be needed to empirically validate weight magnitudes

## R4: Strategic Judgment Validation — COMPLETED (18 April 2026, 22:15 UTC)

### Validation Design
- **Method:** Scenario-based validation with 7-dimension rubric (0–2 per dimension, 14 max)
- **Pass threshold:** 72% (10/14)
- **Mock backend:** `_setBackendStatusOverride()` test hook injected into decision-model.js for R4 harness use

### Weaknesses Found
1. **Candidate action coverage gap:** System defaults to `clear_failed_delivery_queue` for most DEGRADED scenarios — database-specific and worker-health actions are not generated as candidates when those are the real threats. S2 demonstrates this: escalates for database concern but recommends housekeeping.
2. **Conflict reasoning impossible without patterns:** `orderedPatterns` is read from pattern-store, not scenario input, so multi-pattern conflict reasoning never triggers during validation. S1 demonstrates this.
3. **Scenario parameter override limitation:** `makeDecision`'s internal calls to `getSelfCheckResult()` return live system state, partially overriding scenario-provided parameters. S3 demonstrates this: scenario intended to test "first-seen DEGRADED, low restarts" but live system has `worker_restart_count=4`, so system correctly escalates.

### Fixes Applied
1. **Escalation rules** — worker_restart_count > 3 and database health concerns (unhealthy/degraded/elevated_latency) now trigger OPERATOR_REVIEW_REQUIRED with explicit reasoning
2. **Uncertainty acknowledgment** — system explicitly notes when selfCheckResult contains unprocessed fields
3. **Conflict acknowledgment** — when escalation reason doesn't match recommended action, reasoning explicitly states this
4. **Fallback planning** — mode downgrade from recommend_action to DEFER_UNTIL_NEXT_CYCLE when escalation reason exists but action doesn't address it

### Results
